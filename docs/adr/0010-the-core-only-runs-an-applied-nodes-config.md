# 0010 — 核心只运行已应用节点的配置

状态：已接受（闸门与"没有配置就没有核心"规则不变。被否决替代方案中"非接管形态仍然存在"
的段落不再成立：第二种形态与选择它的开关已移除，见
[ADR 0011](0011-tproxy-switch-defaults-on-and-follows-the-core-start.md)）

## 背景

直到 v0.7，模块有一条"直连运行"回退：没有应用任何节点时，核心照样在开机启动，往配置里
渲染一条 freedom 出站，监听本地入站、什么都不做。同一回退存在于五处——开机路径、渲染器、
`kr_ensure_config`、端口路径和换入回滚——每一处都可能把诚实的"什么都没应用"状态静默替换
成一个什么都不代理的运行中核心。

那个状态对用户没有价值：没有节点支撑的本地入站毫无用处，而且它让"运行中"依据用户看不见
的账目而意味着两种相反的事（在代理、不在代理）。

## 决策

**核心绝不运行不是从已应用节点推导出的配置。** "已应用"意味着自洽：`runtime/applied`
指名一个 id，`outbound.meta` 指名同一个 id，`outbound.json` 非空。

- **一个闸门，在启动处。** 没有已应用节点时 `kr_start` 拒绝并记录 `stopped/no-node`。手动
  启动（CLI、Action 按钮、WebUI）撞同一闸门、带消息拒绝；没有节点被应用时 WebUI 停用
  启动按钮。
- **任何地方都没有 freedom 回退。** `kr_render_config` 要求出站存在；`kr_ensure_config`
  拒绝构建无法从已应用节点推导的配置（`failed/no-config`）；端口路径拒绝而不是重渲染成
  直连；没有旧配置的换入回滚让核心保持停止，而不是运行占位物。
- **开关开着且无节点时开机仍保持 fail-closed**（ADR 0004）：规则照样装入，设备没有网络，
  直到用户从本地 WebUI 应用节点——而它不需要网络。跳过规则会让直连流量泄漏，而持久化的
  开关明明写着"接管"。
- **非接管形态仍然存在。** 接管开关关闭的已应用节点（空转）不受影响；废除的只是
  freedom/无节点状态。

## 后果

- 全新安装在用户点按一个节点之前开机什么都不做。WebUI 明说（`stopped/no-node` 与启动按钮
  的提示），而不是一个无意义"运行中"的核心。
- 接管开关开着且无节点时开机，意味着应用节点之前没有网络。这是持久化开关的代价；WebUI
  是本地的、永远可达。
- 过去会清掉 `runtime/applied` 并渲染直连的每一条回退都已移除：已应用账目只能通过重新
  应用一个节点来修复，绝不由 shell 静默处理。
- 升级安装拒绝启动（更新重置了节点库）而不是以直连起来——与全新安装相同的可见结果。

## 被否决的替代方案

- **保留直连运行作为"模块活着"的信号。** 一个监听无用入站的核心不是值得让"运行中"变得
  含糊的信号。
- **以节点库而不是已应用 id 作闸门。** `state.json` 里的节点是意图；核心配置从已应用节点
  派生（ADR 0005）。装满节点却一个都没应用的库仍然没有可运行的东西。
- **开机无节点时跳过 TPROXY 规则。** 对用户更省事，但那是 fail-open：持久化的开关写着
  "接管"，设备却直连出去——恰是 ADR 0004 要阻止的泄漏。
